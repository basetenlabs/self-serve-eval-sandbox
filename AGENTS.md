# AGENTS.md

Setting pr-eval up for someone rather than changing it? Follow [SETUP.md](SETUP.md).

Rules for anyone, human or agent, working in this repo:

- No customer names, customer data or customer-identifying details anywhere: code, docs, sample data, commit messages, branch names or generated reports. Sample data comes from public repositories only.
- Keys come from the environment, never from files in the repo. Never commit keys, tokens or run outputs that contain them.
- The answer never reaches the agent: merged diffs, the PR's tests and the repository clones in `data/repos/` stay outside the agent sandbox; delete that sandbox before uploading hidden tests to a fresh verifier sandbox. `--keep-sandboxes` may retain only verifiers. Agents get no route to GitHub or package registries while they work: Baseten Sandboxes can't limit a sandbox's network yet, so the agent, and every step but the dependency install, runs in the jail (`docker/jail.py`), whose one way out is the model relay (`docker/proxy.py`). The agent never holds a model key or a meter ticket; only the relay does, outside the jail. The one exception is the request's "Names the tests use" list: signatures only, never a body, a value or a changed return type. A change that weakens this needs a test.
- Setup, provider, verifier and judge errors are invalid attempts, never model failures. A task joins a run only after `pr-eval validate` passes it in the trial image.
- Keep it simple to pick up: the quickstart is install, then `pr-eval serve`, and everything else happens on that page. The page and `pr-eval run` go through the same code (`pipeline.py`), so add features there, not in one of them. A change that adds a step for the user needs a good reason.
- Trials run on Baseten Sandboxes, in the team of the key in the environment (`BASETEN_SANDBOX_API_KEY`, else `BASETEN_API_KEY`; `BASETEN_TEAM_ID` picks a team). Nobody connects an account or a workspace of their own. A team's sandboxes are shared with other runs and other tools, so delete only sandboxes carrying both of this tool's labels, the run's id and this machine's (`runtime.trial_sandboxes`); never by name pattern, and never every sandbox in the team. A resumed run keeps its image and region. Tests must not call cloud APIs.
- The page and the report are built from `web/` (React, Tailwind, shadcn-style components) into `eval_sandbox/app.html` and `eval_sandbox/report_template.html`, so `pr-eval` needs no Node. Edit `web/src`, then `cd web && npm ci && npm run build` and commit the built files with it; a unit test fails when they're stale.
- The look is Baseten's site design system (the `/baseten-design` skill). `web/src/styles/baseten.css` is the skill's stylesheet, copied whole and never edited here (the sign-in pages serve this same file, and `texture.png`, in place through `hosted/public.mjs`); `globals.css` locks Tailwind to its tokens and `eval.css` holds the page's own `ev-*` parts. Light only, square corners, White surfaces on the dotted texture, Beausite for text and Geist Mono for labels, the skill's logo and glyphs (no icon set). The page's family is pink (Model APIs). Charts follow the skill's figure rules: green for open models on Baseten, blue for the closed comparison, a pink chip for the difference between them, gold for anything outside (the judges, not-scored attempts), dashed for "not yet".
- Never commit Baseten's licensed Beausite files and never build them into `app.html` or `report_template.html`, which set in Geist (OFL). `hosted/deploy.py` fetches Beausite into the gitignored `hosted/fonts` (`hosted/fonts.mjs`), and `pr-eval serve` declares and serves it only to a person the hosted sign-in let in. The pages before sign-in (sign-in, refused, errors) are Geist only.
- Hosted, the page reads who is asking only from `X-Forwarded-Email`, which the sign-in server in `hosted/` sets; never trust another identity header.
- Before committing, run the unit tests (no cloud, network or keys needed): `python3 -m unittest discover -s tests`, and `cd web && npm run check` after changing `web/`.
